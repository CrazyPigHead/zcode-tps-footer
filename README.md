# zcode-tps-footer

在 ZCode 桌面版（Z.ai 的桌面编码智能体）每条回答的下面显示一行用量统计，样式参考 DeepSeek Harness。本地会话和 Remote SSH 远程会话都能显示：

```
15:40 · 第8轮·12步 · 用时 7分40秒 · 首 token 7秒 · 49 tok/s · GLM-5.3
16:02 · 第3轮·6步 · 编辑 等待确认 8秒 · 用时 1分12秒 · 首 token 2.8秒 · 88 tok/s · GLM-5.3
14:05 · 第9轮·3步 · 思考 22秒 · 用时 2分11秒 · 首 token 4.2秒 · 51 tok/s · GLM-5.3
14:06 · 第9轮·4步 · 终端 运行中 45秒 · 用时 3分04秒 · 首 token 4.2秒 · 51 tok/s · GLM-5.3
```

用词约定（下文反复出现，先定义一次）：

- **轮**（turn）：你发一条消息、智能体完整回答完毕的过程。「第 8 轮」表示这是本会话从开始以来的第 8 轮对话。
- **步**（step）：一轮内的一次模型请求。智能体每调用一次工具，通常要把工具结果发回模型再请求一次，每请求一次算一步。
- **已结算**：轮次结束后，ZCode 把这一轮的最终用量写入数据库，数据从此不再变化。
- **live**：进行中的轮次。它的数据每秒都在变，由本工具实时计算。

> 衍生自 [HuaiPengFei666/zcode-tps-footer](https://github.com/HuaiPengFei666/zcode-tps-footer)（macOS 版，MIT）。本仓库面向 Windows，附一键安装/卸载脚本。仓库目录就是安装目录：MCP 注册和注入到 ZCode 界面的脚本都直接指向克隆下来的文件，装完后这个目录要一直保留。

## 特性

- 安装脚本把一个 MCP server 注册进用户级配置 `~/.zcode/cli/config.json` 的 `mcp.servers`。这个 MCP server 不提供任何工具，唯一作用是充当启动入口：ZCode 每个会话建立 MCP 连接时都会顺带检查数据服务是否在运行，没在运行就自动把它启动。数据服务全局只有一份、常驻后台，崩溃后会被自动重启，长时间无人使用时暂停远端轮询。
- 没有部署副本，也没有配置文件。ZCode 界面直接加载仓库里的 `inject/inject.js`，日志写在仓库 `logs/` 目录。远端主机列表从 ZCode 桌面端的设置里自动解析：在桌面端打开过哪台远端，哪台的用量就会出现在统计行里。
- 本地不用装 Python。数据服务用 Node.js 重写，通过 `node:sqlite` 只读访问本地用量数据库；Python 只在远端服务器上执行（Linux 远端一般自带 python3）。
- Remote SSH 会话的数据在远端完成汇总，远端用量数据库（可能有几百 MB）不会被整个拉回来：一个小脚本被推到远端，在那里把用量算好，只回传结果。脚本按内容 hash 缓存在远端 `~/.cache/zcode-tps-footer/`（先写临时文件再改名，避免读到写了一半的文件；升级后脚本内容变了，缓存文件名随之变化、自动重新上传；7 天以上的旧缓存按修改时间自动清理；目录不可写时改为每次通过 stdin 直接把脚本内容传过去）。正常运行时每轮只发一条执行命令，已结算轮还支持增量回传（见下文「since 增量协议」），每轮往返只有几百字节；本地按 turn_id（全局唯一的 UUID）把远端数据与本地数据合并。
- 子智能体和工作流的子会话同样有统计行。侧边栏和主界面用同一套渲染代码，按 turn_id 直接匹配，进行中的子会话同样实时显示。子会话条目额外带 `上下文 126K (63%)` 字段：官方的上下文容量表只显示在主会话的输入框工具栏上，只读的子会话面板没有输入框、放不下它，这里按同样的计算方法补上。
- 不修改 ZCode 自身的代码。注入脚本把自身的异常全部捕获并忽略，最坏情况只是统计行不显示，不影响 ZCode 正常使用。

## 统计口径

先说总原则：**轮**和**步**的数量与 ZCode 自己的账完全对齐；进行中轮次的数据由三个数据库来源实时计算拼出（本地与远端用同一套算法，详见 `server.mjs` 中 `foldLocal` 的注释）：

- **marker**（`message` 表连接 `part(step-start)`，即消息与「步骤开始」标记的关联）：ZCode 在每步模型请求发出**之前**，就先把 assistant 消息和 `step-start` 部件写入数据库。它定义了「这一步存在」以及这一步的真实起点。统计行里的步数 M 在请求发出时就 +1，最终与轮次结束时 `turn_usage.model_request_count` 记录的请求数完全一致（被 reactive compact 丢弃的步、Start Plan 重试的步也都计入；compact 自带的请求按其 settle 行 +1 修正）。
- **settle**（`model_usage` 表）：每步的模型输出流结束后写入，通过 `assistant_message_id` 与 marker 关联，提供这一步的 token 数、首 token 延迟和 tok/s。步级别的用量数据都来自这里。
- **tool**（`tool_usage` 表）：工具一被调度就先写一行 `running` 状态（流式工具不用等执行完），执行结束后写入最终状态，用来显示「当前正在执行什么操作」。

步内的实时状态按优先级显示：

- 有正在运行的工具：显示 `工具名 运行中/等待确认 + 计时`。工具名做了简化映射——Bash 显示为「终端」、Read 为「读取」、Edit/Write 为「编辑」、Grep/Glob 为「检索」、WebFetch/WebSearch 为「联网」、Agent 为「子智能体」、`mcp__` 开头的为「MCP」，其余工具显示原名。
- 没有工具在跑、但当前步还没结束：显示 `思考 + 计时`（从该步 marker 写入数据库的时刻开始计）。
- 两者都不是（步与步之间的短暂空隙）：显示 `准备 + 计时`；短于 1 秒的间隙会沿用上一次显示的文字，避免频繁闪变。

轮次一开始就能看到统计行，不用等第一步完成。不过第一步完成前条目还没有 turn_id：界面上 `data-turn-id` 属性的值是用户消息 ID 的 ZCode 版本可以立即匹配显示；值是 `turn_<uuid>` 的版本仍要等第一步完成。轮次结束后，实时数据被 `turn_usage` 表的最终值覆盖。

各字段的含义与 [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（MIT）的 `turn-metrics.ts` 保持一致：

- **第 N 轮**：本会话从开始到现在的轮次总数（全量计数，不是当前回合的序号）。
- **M 步**：当前这轮的模型请求次数。
- **用时**：整轮的实际耗时（墙钟时间），包含工具执行时段。
- **tok/s**：各步输出 token 的总和 ÷ 各步解码时间的总和，不含首 token 的等待时间。
- 进行中（live）条目的 tok/s 和首 token 只累计已结算的步；轮数显示的是估算值（历史轮数 + 1），轮次结束后以 `turn_usage` 的最终值为准。

子会话的数据按 `query_source IN (main_turn, subagent, workflow_child)` 白名单过滤，显式排除 `session_title`、`compact` 这类会借用主轮 turn_id 写入数据库的辅助查询——不过滤的话，它们会被误算进主轮，把主轮的 tok/s 算错。

**上下文占用（仅子会话条目显示，如 `上下文 126K (63%)`）**：

- 分子（当前占用的 token 数）= 该轮最后一条已结算 `model_usage` 行的 `input_tokens + output_tokens`，与官方 `getModelUsageContextTokens` 的算法一致。注意 AI SDK v6 的 `input_tokens` 已经包含 cache 读写部分，`cache_read_tokens` / `cache_write_tokens` 两列只是细分数据，不能再加一遍。它和官方输入框旁的容量表一样，反映「最后一步完成时」的占用，因此上下文压缩后的下一步会自然回落。
- 分母（模型上下文窗口大小）不在用量数据库里，由数据服务按与官方相同的优先级顺序读本地文件解析：先看 `~/.zcode/v2/provider_config.json` 里有没有精确 modelId 的配置，没有再按 `~/.zcode/v2/runtime/provider/` 下（远端刷新后的）`zcode-builtin.json` 的 `modelMatch` 正则规则匹配，取最后一个带 `contextWindow` 的命中规则。解析结果按文件的修改时间 + 大小做签名缓存，文件变了自动重读；两级都解析不到时，只显示 K 数、不显示百分比。
- 远端会话轮次的分子由 `remote_fold.py` 在远端算好回传；分母统一由本地根据该轮最后一步使用的模型补上（远端的配置文件版本与本地不同时，这一项可能有展示上的小偏差；官方对 detached workflow child 也做同样的近似）。

## 工作原理

```
ZCode 会话 ──MCP stdio──▶ mcp/supervisor.mjs（每个会话一份，不提供任何工具）
                             │ 请求 127.0.0.1:3117/healthz 做健康检查，未运行则在后台启动；每 60 秒复查一次
                             ▼
                       server/server.mjs（全局单例、常驻后台，只监听 127.0.0.1:3117）
                         ├─ 本地用量库：node:sqlite 只读查询
                         └─ 远端主机：执行缓存在 ~/.cache/zcode-tps-footer/ 的脚本，增量回传 JSON
                             ▲
                             │ HTTP /turns（含进行中轮次的实时数据）
inject/inject.js（界面注入脚本）─┘
  └─ 安装时向 app.asar 里的 index.html 注入一行 <script> 指向仓库内本文件，监听 section[data-turn-id] 绘制统计行
```

1. **MCP 监督者**（`mcp/supervisor.mjs`）：安装脚本把它注册为用户级 MCP server。注册项只指向仓库内的这个文件、不带环境变量，仓库根目录由文件自身所在位置推算。每个 ZCode 会话各起一份，握手时不提供任何工具。它的职责是保证数据服务在运行：先请求 `127.0.0.1:3117/healthz` 检查，服务没在跑就在后台把数据服务启动起来（监督者自己退出或被杀都不影响数据服务），之后每 60 秒做一次看门狗检查；会话结束时 MCP 的 stdio 通道关闭，监督者随之退出。
2. **数据服务**（`server/server.mjs`）：全局单例、常驻后台，只监听 `127.0.0.1:3117`。本地用量库用 `node:sqlite` 只读查询；远端主机列表从 ZCode 桌面端设置（`~/.zcode/v2/setting.json` 的最近 SSH 会话）自动解析。每台远端独立并行轮询，轮询间隔分三档：ZCode 界面正在使用且该远端有进行中的轮次时 2.5 秒；界面活跃但该远端没有进行中的轮次时 10 秒（已结算轮的数据不会变化，慢慢查有没有新轮次就够了）；界面不活跃时 20 秒。某台远端连接失败时按指数退避重试并保留旧数据，只对它自己退避，其他远端照常轮询。`/turns` 超过 10 分钟没人请求时，远端轮询全部暂停，任何请求一来立即恢复。进行中的轮次由服务实时计算（响应中标记 `live:true`）。端口被占用就主动退出：多个会话同时冷启动时，抢不到端口的那个进程自动退出，以此保证全局只有一份。配套的 `server/remote_fold.py` 是推到远端执行的汇总脚本，只用 Python 标准库：按内容 hash 缓存在远端 `~/.cache/zcode-tps-footer/`（先写临时文件再改名；升级后 hash 变了自动重传；7 天以上的旧缓存按修改时间自动清理；目录不可写时改为每次通过 stdin 直接传脚本内容）。已结算轮按 since 增量回传（协议见下文「since 增量协议」），`/turns` 对界面脚本同样支持 `&since=` 增量。远端不驻留任何进程。
3. **注入脚本**（`inject/inject.js`）：安装时在 ZCode 界面的 `index.html` 里加一行 `<script>`，直接指向仓库内这个文件（会重新打包 app.asar，原包自动备份，不往别处部署副本）。它监听界面上的 `section[data-turn-id]` 元素，按 turn_id 或用户消息 ID 找到数据库里对应的轮次，把统计行画在每条回答底部；取数同样带 since 增量合并（协议见下文「since 增量协议」）。以后改这个文件不需要重新打包 asar，完全重启 ZCode 就生效。
4. **安装/卸载脚本**（`scripts/install.ps1` / `uninstall.ps1`，配合 `mcp-register.mjs` 增删配置文件条目）：一键安装（注册用户级 MCP + asar 注入），一键还原。

## since 增量协议

先说背景：已结算轮一旦写入数据库就不再变化，每秒都在变的只有 live 条目。增量传输正是利用这一点——正常运行时每次只传 live 条目和新出现的轮次（实测 92 个轮次的全量数据约 40KB，稳定后的增量只有 0.6~1.6KB）。

协议里的「**水位**」（since）指调用方上次同步到的时间点（epoch 毫秒）：下次请求把它带上，对端就只回传这个时间点之后可能有变化的数据。同一套协议用在两段链路上：远端 → 数据服务（走 ssh，水位放在命令行参数里）、数据服务 → 界面脚本（`/turns?since=`，水位放在 URL 查询参数里）。

**请求与响应**：调用方带上次返回的水位 `since`（epoch 毫秒），收到的是：结束时间不早于 `since - 边距` 的已结算轮 + **全部** live 条目（live 条目每次都在变，因此每次必带）+ 新的水位。不带 `since`、或响应里 `full:true` 时，返回的是全量快照，调用方整体替换本地数据；否则做增量合并。水位始终按全量数据计算：远端对窗口内**全部**已结算轮（包括被过滤掉的）取最大的 `completed_at`，不会因为过滤而回退，没有已结算轮时取当前时刻；`/turns` 这一侧取合并结果里最新的 `end_ms`——live 条目的 `end_ms` 就是它的计算时刻，必然晚于任何已结算轮，拿它作为下次过滤的起点不会漏掉新完成的轮次。

**5 分钟边距**（`INC_MARGIN_MS`，在 `remote_fold.py` / `server.mjs` / 界面脚本三处取相同值）：过滤时把时间点往前多回看 5 分钟。原因是新完成轮次的 `completed_at` 并不总晚于调用方已知的水位——多个会话交错时，B 轮可能比 A 轮刚产生的水位完成得更早。边距内的条目每次都会重发，调用方按 key 直接覆盖，多收几条没有副作用。

**合并语义**：以 `turn_id` 为 key；第一步还没结算、尚无 turn_id 的 live 条目用 `msg_id` 代替。后到的数据覆盖先到的；同一轮次的 live 版本和已结算版本按 turn_id / msg_id 双向去重——轮次结束时 live 条目被最终数据原地替换，不会留下两份。服务端的 `mergeRemoteTurn` 和界面脚本的 `mergeTurns` 实现逻辑相同。

**多层自动恢复**（增量传输正确性的关键——任何一层出问题都只该造成分钟级的数据延迟，而不是永久丢数据）：

| 链路 | 机制 | 防范的问题 |
| --- | --- | --- |
| ssh（数据服务→远端） | 任何失败都立即把水位清零，下次成功时必然改走全量 | 水位本身已经错误 |
| ssh（数据服务→远端） | 每 10 分钟（`FULL_SYNC_MS`）强制做一次全量 | 增量状态长期累积的误差 |
| ssh（数据服务→远端） | 移除 26 小时（`EVICT_MS`）以前的旧条目（比远端 24 小时的汇总窗口多留 2 小时） | 旧条目滑出远端汇总窗口后残留 |
| /turns（数据服务→界面脚本） | 取数出现异常时把水位归零 | 收到不完整的响应 |
| /turns（数据服务→界面脚本） | 连续 3 次整页数据没有任何匹配、且距上次全量超过 30 秒时归零 | 水位异常导致漏数据 |
| /turns（数据服务→界面脚本） | 每 5 分钟（`FULL_REFETCH_MS`）定期归零一次 | 不同机器之间的时钟偏差 |

周期性全量刷新不可省略：水位混合了本地和各台远端的时钟，只要有一个数据源的时钟比其他快 5 分钟（边距）以上，时钟慢的那台新完成的轮次就会被增量响应**永久**过滤掉，而且上表「连续 3 次整页没有任何匹配」的恢复机制也救不回来——页面上任何旧轮次匹配到都会重置计数。周期性把水位归零，能把最坏情况下的漏发窗口限制在 5 分钟以内。

**live 条目超时未刷新的检测与移除**：live 条目的 `end_ms` 每次回传都会刷新为远端汇总的时刻，轮询正常时秒级刷新（轮询失败时不参与移除判定，故障期间旧数据原样保留）。超过 5 分钟（`LIVE_FREEZE_MS`）没有刷新，说明远端已不再产生这个条目，就及时把它移除——避免已经中断的「运行中」条目一直计时，直到定期全量刷新才消失。判定时会按每台远端采样到的本地-远端时钟偏移，把时间换算到同一时钟域再比较（凡是带 live 条目的响应都顺便提供一次采样），所以远端时钟偏快或偏慢都不影响正确性。

## 前置要求

- Windows + ZCode 桌面版（官方安装包）
- Node.js ≥ 23.4，`node` 在 PATH 上：MCP 监督者、数据服务、用 `npx asar` 解包/打包都要用它
- 克隆下来的目录要一直保留：MCP 注册和 asar 注入都指向仓库内文件，移动或删除仓库等同于卸载（换了位置重跑一遍 `install.ps1` 就行）
- 远端服务器（可选）：SSH 免密可登录（`ssh <user>@<host> echo ok` 不输密码就通），装有 python3（Linux 发行版标配）
- 本地不需要 Python

## 安装

```powershell
cd <仓库目录>
powershell -ExecutionPolicy Bypass -File scripts\install.ps1
# 若 ZCode 正在运行：先完全退出再跑，或直接加 -KillZCode
# 探测不到安装目录时：-ZCodeDir "D:\ProgramFiles\ZCode"
# 完成后完全退出 ZCode 再打开
```

脚本依次做三件事：注册用户级 MCP server（配置键 `mcp.servers.zcode-tps-footer`，只增删本项目的条目，其他设置原样保留）、启动数据服务、向 app.asar 注入脚本标签。

装完必须完全退出并重启 ZCode：注入到界面的脚本行要重启才会加载，MCP 注册也要等新会话建立连接才生效。

运行时产生的文件只有日志与开关状态，在仓库 `logs/` 目录（已 gitignore）：

```
<仓库目录>\logs\
  ├── server.log      数据服务日志
  ├── tps-state.json  统计行开关状态（/tps-state 写入，见下）
  └── supervisor.log  MCP 监督者日志
```

### 排障：统计行 A/B 开关

排查界面问题（如闪烁、卡顿）时，可以不重启 ZCode，直接把全部统计行临时撤掉/恢复，做对比测试：

```powershell
curl.exe -X POST "http://127.0.0.1:3117/tps-state?enabled=0"   # 撤掉全部统计行（≤2s 生效）
curl.exe -X POST "http://127.0.0.1:3117/tps-state?enabled=1"   # 恢复
curl.exe "http://127.0.0.1:3117/tps-state"                     # 查询当前状态
```

撤掉后问题仍在，说明与注入无关（是应用原生行为）；撤掉后问题消失，说明是注入侧的问题。开关状态随 `/turns` 响应下发给界面脚本，并持久化在 `logs/tps-state.json`，服务重启后保持。2026-09 排查「侧边栏闪烁」用的就是这个方法：撤掉注入后依然闪烁，确认是 ZCode 原生渲染行为（滚动渐隐 mask 导致整层重绘、虚拟列表先按估算高度排版再跳变为实测值等，见 `ConversationTimeline.tsx`），与注入无关。

### 远端主机：零配置，自动识别

远端列表从 ZCode 桌面端设置（`~/.zcode/v2/setting.json` 的最近 SSH 会话列表）自动解析：在桌面端打开过一台新远端，它的用量就会自动进统计行，不需要任何配置。两点注意：

- 最近会话列表有淘汰机制。老远端被新会话挤出列表后就不再被轮询；常用的远端偶尔在桌面端打开一次，就能保持在列表里。
- 连不上的远端不会拖累其他远端。各远端独立并行轮询，单台失败只对它自己退避，`/status` 里能看到各远端的 `error` 详情。

## 数据服务生命周期

| 事件 | 行为 |
| --- | --- |
| ZCode 会话建立 MCP 连接（启动、新建或恢复会话） | 监督者检查服务是否在运行，没在运行就启动 |
| 服务崩溃 | 会话内的看门狗每 60 秒检查一次，连续 2 次失败即重启服务 |
| ZCode 全部关闭 | 服务留在后台但进入闲置：10 分钟后暂停远端 SSH 轮询（不保持任何连接），本地零 CPU |
| 再次打开 ZCode | 首个会话建立连接即恢复轮询；`/turns` 请求本身也会立即恢复轮询 |
| 多个会话同时冷启动 | 各实例抢绑端口，抢不到的那个自动退出，保证单例 |

## 日常改动与生效方式

| 改动 | 生效方式 |
| --- | --- |
| ZCode 桌面端打开过新远端 | 自动出现在统计行（解析 `~/.zcode/v2/setting.json`），什么都不用做 |
| 仓库里的 `server.mjs` / `supervisor.mjs` / `remote_fold.py` | 重跑 `install.ps1`（会顺带重启数据服务以加载新代码；ZCode 正在运行时脚本会在 asar 注入这一步安全停下，先完全退出 ZCode 或加 `-KillZCode` 再跑） |
| 仓库里的 `inject/inject.js`（样式/字段） | 只需完全退出 ZCode 重开，不涉及服务与 asar |

## 卸载

```powershell
powershell -ExecutionPolicy Bypass -File scripts\uninstall.ps1
# 移除 MCP 注册 + 按版本恢复原始 app.asar + 停止数据服务（仓库内的配置与日志保留）
```

以后不用了，直接删掉整个仓库也行。

## ZCode 更新后

整包更新会覆盖 app.asar，统计行会消失，但不影响 ZCode 本身使用，重跑一遍 `install.ps1` 就能恢复（脚本自动检测并重新注入，MCP 注册不受影响）。重跑时，官方原包的备份 `resources\app.asar.tps-bak.v<版本>` 会同步更新为新版，旧版本的备份自动删除；之后再卸载，恢复的就是新版原包，不会把 ZCode 回退到旧版本。

## 常见问题

- **统计行没出现**：先确认完全重启过 ZCode，界面注入和 MCP 注册都要重启或新会话才生效。再看服务在不在跑：`curl --noproxy "*" http://127.0.0.1:3117/healthz`（本机有代理时必须带 `--noproxy "*"`，否则探测结果会被代理干扰）。`/status` 可以看各数据源的健康状况（`ok_age_s` / `consec_fail` / `error`）。日志在仓库 `logs/` 目录下（`supervisor.log`、`server.log`），MCP 注册项在 `~/.zcode/cli/config.json` 的 `mcp.servers`。
- **远端会话没有统计行、本地有**：先确认该远端出现在 `/status` 的 remotes 里，没有就说明桌面端还没打开过它，用桌面端连一次即可被识别。再看该远端的 `error`：`ssh rc=...` 多半是需要密码或 known_hosts 变更，`remote: ...` 是远端侧读库问题。可以手动验证免密登录是否正常：`ssh <user>@<host> "python3 -c 1"`。
- **首次安装后第一个会话没有启动服务**：个别情况下，首次安装后的第一个 MCP 连接是「幻影连接」——ZCode 的信任确认流程还没走完，连接并不会真正启动进程；信任确认之后的下一个会话会自动恢复正常。手动解决办法就是重跑 `install.ps1`。
- **移动过仓库**：直接重跑一遍 `install.ps1` 即可。注入标签带独立标记（`data-tps-footer`），检测不依赖目录名，脚本会自动把指向旧位置的注入改写为当前位置。
- **想改统计行样式/字段**：编辑仓库里 `inject/inject.js` 的 `render()`，重启 ZCode 生效。

## 回归与调试

`tools/regress/` 是修改统计逻辑前用来做语义验证的小工具：

- `capture.mjs` 抓取 `/turns` 的数据快照，`diff.mjs` 对两次快照做规范化对比（非 live 条目要求逐个字段严格相等，live 条目容忍随时间变化的字段）。修改 `server.mjs` 的汇总逻辑前后各抓一份快照，就能验证统计结果没有变化。
- `mcp-test.mjs` 验证监督者的生命周期（`node tools/regress/mcp-test.mjs`，需要 3117 端口空闲）。
- `killnode.ps1` 测试前清理环境（结束残留的 node 进程）。

## 兼容性

- 适配 ZCode 3.11.x – 3.14.x（Electron 41+）。大版本更新后如果界面元素 `section[data-turn-id]` 的结构变了，需要相应更新 `inject.js` 里的选择器。
- 进行中轮次的实时统计依赖消息数据库里有 `step-start` part 记录（本仓库适配的 3.11.x+ 版本都有）。远端如果运行更老的 ZCode，该会话就只有已结算轮的统计，没有进行中轮次的实时条目。
- `data-turn-id` 的值在不同版本间可能是 `turn_<uuid>`，也可能是用户消息 ID（`msg_xxx`），匹配逻辑对两种都兼容。
- 数据服务和 MCP 监督者只用 Node 标准库（含 `node:sqlite`），跨平台、无原生依赖；远端取数只依赖 SSH + python3 标准库，远端不留常驻进程，只留一个按内容 hash 命名的缓存脚本（`~/.cache/zcode-tps-footer/`，可以随手删，删后下一轮自动重建）。安装脚本目前只支持 Windows（PowerShell），macOS/Linux 可以参考上游仓库。
